01

Flutter en 60 secondes

Flutter est le framework UI open source de Google. Il ne dessine pas des composants natifs : il dessine lui-même chaque pixel. C'est la clé de tout le reste.

Dart — typé statiquement, null safety par défaut, compilation native AOT et web via JS/Wasm
Rendu
Impeller — devenu le moteur par défaut sur macOS, Windows et Linux. Rendu GPU direct, pas deshaders Skia

Android · iOS · Web · Windows · macOS · Linux — une seule base de code

Injection de code à chaud en < 1 seconde : le state est conservé, l'UI se redessine seule

Flutter ≠ React Native. React Native affiche des composants natifs de la plateforme ; Flutter peint lui-même l'interface. D'où une rendu identique partout, des animations plus fluides, et un « look » qui n'est ni iOS ni Android tant que tu ne l'imposes pas.

02

Le modèle mental : de ton code aux pixels

Flutter a trois arbres en parallèle. Les comprendre, c'est comprendre pourquoi Flutter est rapide, et pourquoi un setState peut reconstruire toute l'interface.

Le point crucial : un widget est immuable. Tu ne modifies jamais un widget — tu en crées un nouveau. Flutter compare l'ancien et le nouveau element pour décider quoi repeindre. C'est pour ça que « changer une variable » en Dart ne change rien à l'écran : il faut passer par setState(), ValueNotifier ou un gestionnaire d'état.

03

Les définitions techniques

Le vocabulaire Flutter est trompeur : « state », « widget », « rebuild » ne veulent pas dire ce que tu crois. Voici les 22 termes qu'il faut maîtriser, définis une fois pour toutes.

Widget
Une description immuable d'une partie de l'interface. C'est une simple classe Dart : pas de méthode, pas de référence mutable. « En Dart, on n'écrit pas des widgets, on écrit des descriptions de widgets. »
StatelessWidget
Un widget dont l'UI ne dépend d'aucun état mutable. Il se reconstruit à l'identique tant que son parent ne change pas. Exemple : un titre, une icône, une carte statique.
StatefulWidget
Un widget qui possède un objet State séparé. C'est lui qui survit aux reconstructions et qui déclenche les changements d'UI.
State
L'objet qui contient les données variables d'un StatefulWidget. Il est conservé par l'element tant que le widget garde la même identité (même type + même Key).
setState
La méthode qui marque l'UI comme sale et demande une reconstruction. À appeler uniquement depuis le State. Elle est asynchrone : le rendu a lieu au prochain frame.
BuildContext
Le pointeur vers l'element d'un widget dans l'arbre. Il sert à retrouver un thème, un provider, une route, une MediaQuery. Il est invalide si utilisé après le démontage du widget.
Element
Le pont entre le widget et le render object. Il porte l'identité (position + Key) et le cycle de vie (montage, activation, désactivation, démontage).
RenderObject
L'objet qui connaît la taille, la position et la peinture d'un widget. Il fait le layout et le paint. Il ne connaît rien au Dart métier.
Constraints
Les bornes imposées à un widget par son parent (largeur min/max, hauteur min/max). Combinées aux size de l'enfant, elles produisent la taille finale.
Layout
La phase où Flutter calcule la taille et la position de chaque render object. RenderBox.performLayout en est le cœur.
Key
Un identifiant unique pour un widget dans son parent. Il permet à Flutter de réutiliser le State quand la liste est réordonnée, au lieu de tout reconstruire. Deux types : ValueKey et ObjectKey.
Sliver
Un widget de liste qui construit ses enfants à la demande selon le scroll. ListView.builder n'en crée que quelques-uns, pas 10 000.
InheritedWidget
Un widget qui transmet une donnée à ses descendants sans les reconstruire. C'est le mécanisme historique sur lequel repose Theme, MediaQuery et le package provider.
Navigator
Le gestionnaire de routes : il empile les écrans (pages) et gère le retour arrière. Navigator.push / pop. Depuis peu, go_router est préféré pour les apps sérieuses.
Route
Une page de l'application, avec sa propre NavigatorState. Elle peut être empilée, remplacée ou utilisée comme dialogue.
Hot Reload
Injection du code modifié dans le Dart VM en cours d'exécution. L'état est conservé, l'UI se reconstruit. Hot Restart relance l'app et perd l'état.
Null safety
Le type String? accepte null, le type String non. Actif par défaut depuis Dart 2.12. Le ? est obligatoire pour le nullable, ! force l'absence de null.
Future
La promesse de Dart : une valeur qui sera disponible plus tard. await l'attend. async/await remplace les callbacks imbriqués.
Stream
Une suite de données émises dans le temps. StreamBuilder s'y abonne et se reconstruit à chaque émission. Indispensable pour le temps réel.
Impeller
Le moteur de rendu de Flutter (défaut sur desktop depuis la 3.47). Il compile les shaders pour le GPU et gère les effets. Remplace Skia.
Isolate
Un fil d'exécution Dart indépendant, sans mémoire partagée. Indispensable pour ne pas bloquer l'UI lors d'un calcul lourd (parsing JSON lourd, cryptographie).
Rebuild
La reconstruction de l'UI. Flutter ne reconstruit que ce qui a changé : c'est le rôle de l'equality des widgets et des Key. D'où l'importance de const.
04

La chaîne en 7 étapes

L'ordre compte : le Dart d'abord (sans quoi rien ne compile), puis les widgets, puis l'état, puis le réseau. Chaque étape se termine par un jalon que tu dois atteindre avant de passer à la suite.

  1. Étape 1 — D'abord le langage Dart

    ~30 h
    • Variables, types, null safety, final vs const, late.
    • Fonctions, paramètres nommés, fonctions fléchées, closures.
    • Classes, constructeurs, named constructors, héritage, mixins.
    • Listes, maps, final, where, map, fold.
    • async/await, Future, Stream, gestion d'erreur (try/catch).

    Ressources

    Dart — le langage (officiel) Dart — tutoriel interactif Dart en 10 min — Technovore FR · 10 min Cours Dart FR complet GitHub

    Jalon 1 — un script Dart en ligne de commande qui lit un JSON, le transforme et affiche un résultat. Tu écris des classes avec des constructeurs nommés sans hésiter.

  2. Étape 2 — L'environnement et les premiers widgets

    ~15 h
    • Installer Flutter SDK + un IDE (VS Code, Android Studio, IntelliJ).
    • flutter doctor pour vérifier que tout est bon.
    • Comprendre la structure d'un projet : lib/, pubspec.yaml, android/, ios/.
    • Écrire ses premiers widgets : Text, Container, Column, Row, Stack.
    • Lire pubspec.yaml et ajouter un package avec flutter pub add.

    Ressources

    Installation (officiel) Premier projet App mobile de A à Z — Ralph Développeur FR · 15 min Codelabs interactifs (officiel)

    Jalon 2 — une app qui s'affiche sur Android, iOS et le web avec le même code, et qui tourne en flutter run -d chrome sans configuration.

  3. Étape 3 — La mise en page et la navigation

    ~25 h
    • Comprendre Row vs Column, Expanded, Flexible, Stack, Wrap.
    • Maîtriser les constraints : c'est LA source de 80 % des bugs de mise en page.
    • Listes : ListView.builder, GridView, SliverList, séparation avec ListView.separated.
    • Navigation : Navigator.push, routes nommées, passage d'arguments, retour de résultat.
    • Formulaires : TextFormField, Form, validation, GlobalKey<FormState>.

    Ressources

    Layout — la référence ListView + navigation — Technovore FR · 17 min Cookbook — navigation Cookbook — validation de formulaires

    Jalon 3 — une app à 3 écrans avec navigation, une liste de 100 éléments qui scroll fluide, et un formulaire validé. Tu sais expliquer un overflow sans chercher sur Google.

  4. Étape 4 — L'état : le cœur de Flutter

    ~30 h
    • Comprendre setState, initState, didChangeDependencies, dispose.
    • Le cycle de vie d'un State — et pourquoi dispose() n'est pas optionnel.
    • Passer de setState à ChangeNotifier + provider.
    • Choisir son approche : Riverpod ou BLoC (voir le comparatif plus bas).
    • Extraire la logique métier hors des widgets (pattern ViewModel).

    Ressources

    État simple (officiel) Riverpod — documentation BLoC — documentation Architecture — la couche UI (officiel)

    Jalon 4 — ton compteur, ton panier ou ton thème fonctionnent avec un gestionnaire d'état, pas avec des setState éparpillés. Tu sais expliquer le flux de données dans ta tête.

  5. Étape 5 — Les données : réseau et stockage

    ~30 h
    • Appeler une API REST avec http ou dio, gérer loading / success / error.
    • Modéliser les données avec fromJson / toJson et json_serializable.
    • Stocker localement : shared_preferences (clé/valeur), sqflite (SQLite), hive, drift.
    • Injection de dépendances pour tester : le réseau est.mockable.
    • Gérer l'auth : token stocké, intercepteur qui l'ajoute à chaque requête, refresh.

    Ressources

    Appeler une API (officiel) Dio — client HTTP Retrofit — API typée Sqflite — SQLite

    Jalon 5 — ton app affiche une liste de données venant d'une vraie API, avec un état de chargement, une gestion d'erreur propre et un cache local qui fonctionne hors ligne.

  6. Étape 6 — La qualité : tests et performance

    ~20 h
    • Tests unitaires (logique métier), widget (rendu) et golden (pixel par pixel).
    • Mesurer avec le DevTools : arbre des widgets, timeline du rendu, profile mémoire.
    • Optimiser : const sur les widgets statiques, ListView.builder, éviter les rebuilds inutiles.
    • Travailler les animations : implicites, AnimationController, Hero.
    • Accessibilité : Semantics, contrastes, cibles tactiles.

    Ressources

    Tests (officiel) Bonnes pratiques perf Animations (officiel) DevTools

    Jalon 6 — un flutter test qui passe au vert, un profil DevTools qui montre 60 fps constants, et une animation Hero entre deux écrans.

  7. Étape 7 — Architecture et mise en production

    ~25 h
    • Structurer en couches : presentation / domain / data.
    • Séparer la logique métier des widgets — la règle qui fait tenir une app à 50 000 lignes.
    • Gestion de la taille d'écran, du mode sombre, de l'internationalisation.
    • Build de production : flutter build apk, appbundle, ipa, web.
    • CI/CD, signature, stores (Play Store, App Store).

    Ressources

    Architecture d'app (officiel) Déploiement (officiel) Modes de build Cours Flutter FR — 12 chapitres GitHub

    Jalon 7 — une app publiée sur le Play Store (ou prête à l'être), avec une architecture en couches, des tests, et un README qui explique comment la lancer.

05

Dart d'abord, ou Flutter d'abord ?

La question revient systématiquement. Voici la réponse honnête, selon ton profil.

Tu débutes en programmation

Commence par Dart seul. Un seul langage à appris, sans framework, sans widget, sans moteur de rendu.

  • 1 à 2 semaines sur les fondamentaux du langage
  • Pas de « pourquoi mon widget ne s'affiche pas ? »
  • Tu arrives sur Flutter avec du confort, pas avec du doute

Tu connais déjà un langage moderne

Tu peux aller directement sur Flutter et apprendre le Dart en chemin. C'est ce que recommande le parcours officiel.

  • Le « Dart Getting Started » est facultatif dans ce cas
  • La syntaxe se lit comme du Kotlin, du TypeScript ou du Swift
  • Mieux vaut voir le résultat tout de suite

Tu viens du web / React

Le piège classique : tu veux tout faire en StatelessWidget + setState, comme du React.

  • Flutter est impératif : on construit une hiérarchie de widgets
  • Le state est une donnée, pas un useState
  • Prends le temps de l'étape 4 (état), c'est là que ça se joue

Le parcours officiel Flutter (docs.flutter.dev/learn/pathway) est exactement structuré en trois temps : environnement → tuto Dart → tuto Flutter. C'est la référence officielle, gratuite, et elle suit ce découpage. Si tu veux une seule source à suivre, c'est celle-ci.

Choisir son gestionnaire d'état

En 2026, trois solutions dominent. Le mauvais choix te coûte des semaines ; voici comment choisir.

CritèreProviderRiverpodBLoC
Version stable 20266.1.53.3.19.1.1
Sécurité à la compilationNon (échec à l'exécution)OuiOui
Lecture hors du widget treeNonOuiLimité
Injection de dépendancesOui (simple)IntégréeNon (package séparé)
Flux event → stateNonPartiellementOui (strict)
Historique du state traçableNonLimitéOui
Courbe d'apprentissageTrès douceMoyennePlus raide
Verdict 2026Projets existing, legacy, pédagogieNouveau projet, la plupart des casGrande équipe, logique complexe, audit requis

Mon conseil : apprend ChangeNotifier + provider d'abord (c'est la base de Riverpod, et ça se lit dans le SDK Flutter). Ensuite passe à Riverpod pour tes vrais projets. Ne commence pas par BLoC : le ceremony Event → Bloc → State est un vrai coût d'apprentissage, et il ne se justifie que sur une grosse équipe avec des besoins d'audit.

07

Les projets fil rouge

Un seul projet que tu fais grossir, étape par étape. C'est ce qui fait retenir — pas une nouvelle app à chaque tutoriel.

Étapes 1 – 2

Compteur & fiche produit

Premier StatefulWidget, premier setState, premier const. Tu poses les bases.

Étape 3

Catalogue de produits

ListView.builder, GridView, page détail avec arguments de route.

Étape 4

Panier d'achat

Le state devient complexe : tu passes à Riverpod et tu compares avec BLoC.

Étape 5

Connexion à une vraie API

Token, intercepteur Dio, cache shared_preferences, états loading / error.

Étape 6

Animations & tests

Transition Hero, animation implicite, tests widget et golden.

Étape 7

Release

Architecture en couches, flutter build appbundle, publication.

08

Les six pièges du débutant

Ce sont les erreurs qui reviennent le plus souvent — et qui coûtent le plus de temps.

Modifier une variable sans rebuild

Changer count = 5 ne change rien à l'écran. Un widget est immuable : il faut setState().

Oublier dispose()

Un Timer, un StreamSubscription ou un ScrollController non libérés fuient et plantent à la fermeture.

ListView(children: [...]) avec 10 000 items

Tout est construit d'un coup → freeze et pic mémoire. Utilise ListView.builder, qui construit à la demande.

const oublié

Sans const, Flutter ne peut pas savoir que le widget n'a pas changé et le reconstruit inutilement.

Logique métier dans le widget

Un build() de 200 lignes est un build() qui ne se testera jamais. Extraire dans un ViewModel.

Attendre le réseau dans build()

Un FutureBuilder lancé dans build() relance une requête à chaque reconstruction.

Mémo des commandes

La CLI Flutter, en un coup d'œil.

# Créer et lancer un projet
flutter create mon_app
cd mon_app
flutter run                  # sur l'appareil / émulateur par défaut
flutter run -d chrome        # dans le navigateur (le plus rapide pour débuter)
flutter run -d windows       # sur le bureau
flutter run --release

# Ajouter / retirer des paquets
flutter pub add dio
flutter pub add --dev flutter_lints
flutter pub get             # installé les dépendances
flutter pub outdated
flutter pub upgrade --major-upgrades

# Qualité
flutter analyze              # linter intégré
flutter test                # tests unitaires + widget
flutter test --coverage
dart format .

# Build de production
flutter build apk            # APK Android
flutter build appbundle      # AAB pour le Play Store
flutter build ipa            # iOS (nécessite macOS + Xcode)
flutter build web
flutter build windows

# Divers
flutter doctor               # vérifie l'environnement
flutter devices              # liste les cibles disponibles
flutter clean               # nettoie les artefacts de build
flutter --version
Structure lib/
lib/main.dart (point d'entrée) · lib/models/ · lib/views/ · lib/widgets/ · lib/services/ · lib/providers/
pubspec.yaml
Le manifeste : nom, version, assets, dépendances. flutter pub add l'édite tout seul — ne le modifie pas à la main pendant que le build tourne.
Assets
Déclarés dans pubspec.yaml sous flutter: assets:, puis chargés avec rootBundle ou Image.asset
Android / iOS
Les dossiers android/ et ios/ contiennent la config native (permissions, nom de l'app, signature). On y touche rarement.
Plateformes
flutter create --platforms web,android pour ne générer que celles qui te servent
10

Checklist de validation

Coche ces cases : si elles sont toutes cochées, tu es prêt pour un poste Flutter.

  • Je peux expliquer la différence entre Widget, State et Element sans hésiter.
  • Je sais pourquoi setState() est nécessaire, et où il ne l'est pas.
  • Je sais expliquer un RenderFlex overflowed et le corriger.
  • Je sais dire quand utiliser Row et quand Column, et pourquoi ça déborde.
  • Je sais passer des données entre deux écrans et en récupérer au retour.
  • Je sais valider un formulaire et afficher les erreurs champ par champ.
  • J'ai utilisé un gestionnaire d'état autre que setState seul.
  • Je sais expliquer la différence entre Provider, Riverpod et BLoC, et choisir.
  • Je sais appeler une API et gérer les états loading / success / error.
  • Je sais stocker une donnée localement et la relire au démarrage.
  • Je libère mes ressources dans dispose().
  • J'ai écrit au moins un test unitaire et un test widget.
  • Je sais utiliser ListView.builder et expliquer pourquoi il ne freeze pas.
  • Je sais construire un appbundle et le préparer pour le Play Store.
  • Je sais organiser mon code en couches (UI / domaine / données).
